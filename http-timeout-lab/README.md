# HTTP timeout lab: где запрос ждёт, когда CPU свободен


Самодостаточная лаборатория на стандартной библиотеке Go. Программа измеряет один HTTP/1.1-запрос от начала клиентской операции до полного чтения `response.Body` и завершения `Close`. Она сохраняет исходные события `httptrace`, ошибки каждого этапа и точные выборочные p50/p95/p99.

Задержки локальных серверов **введены искусственно**. Числа в выходном каталоге получаются настоящим запуском программы. Это диагностические эксперименты на localhost: по ним нельзя оценить пропускную способность своего сервиса или частоту сетевых сбоев в production.

## Быстрый запуск

Минимальная версия, объявленная в `go.mod`, — Go 1.23.0. Основная серия, тесты, `-race`, `go vet` и сборка выполнены на **Go 1.26.5, darwin/arm64**. CPU и сеть измерены отдельно на **Go 1.27.4, linux/arm64**. Конфигурация каждого нового запуска сохраняется в `metadata.json` его выходного каталога.

```sh
go version
go test -buildvcs=false ./...
go test -buildvcs=false -race -count=1 ./...
go vet ./...
go build -buildvcs=false -o timeoutlab .
./timeoutlab suite -out results-new
```

Внешних Go-модулей нет; файл `go.sum` не нужен. Для `-race` необходима поддерживаемая платформой конфигурация Go с C-компилятором. Флаг `-buildvcs=false` отключает добавление сведений о родительском Git-репозитории в бинарник; на измеряемую логику он не влияет.

`suite` создаёт десять локальных серверных сценариев по очереди, выполняет 1690 измеряемых запросов и завершает работу. Все серии включают начальное установление соединений; отдельного прогрева нет. В одном сценарии используется общий `http.Client` и общий `http.Transport`. Между сценариями транспорт и сервер создаются заново.

## Что воспроизводит suite

| Сценарий | n / c | Контролируемое условие | Что смотреть |
|---|---:|---|---|
| `baseline` | 200 / 8 | 5 ms до заголовков, лимит 8 соединений | Исходный профиль задержек и reuse |
| `rare_headers` | 500 / 8 | Дополнительно 300 ms до заголовков для каждого 50-го ID | p99 и `request_to_first_byte` |
| `rare_body` | 500 / 8 | Дополнительно 300 ms после отправки и flush первого байта тела для каждого 50-го ID | p99 полной операции и `body_ms`; заголовки приходят быстро |
| `pool_1` | 100 / 8 | 25 ms на сервере, `MaxConnsPerHost=1` | Длительный `GetConn → GotConn` при reuse |
| `pool_8` | 100 / 8 | Те же 25 ms, `MaxConnsPerHost=8` | Изменение ожидания выдачи соединения |
| `tls_reuse` | 100 / 1 | HTTPS; 30 ms в серверном TLS callback, 5 ms перед HTTP-ответом | Один handshake, следующие 99 запросов используют соединение |
| `tls_no_reuse` | 100 / 1 | Те же условия; `DisableKeepAlives=true` | 100 установлений TCP/TLS |
| `dns_delay` | 50 / 1 | Новый connection на каждый запрос; локальный DNS отвечает через 25 ms; HTTP-сервер — через 2 ms | Настоящие `DNSStart`/`DNSDone` |
| `header_timeout` | 20 / 4 | Сервер ждёт 150 ms до заголовков, `ResponseHeaderTimeout=40ms` | 20 ошибок `Client.Do` |
| `body_timeout` | 20 / 4 | Первый байт тела отправлен сразу, оставшееся тело ждёт 150 ms, `Client.Timeout=50ms` | 20 ошибок чтения тела при уже полученном HTTP 200 |

В двух rare-сценариях медленными являются ровно ID 50, 100, …, 500: 10 из 500, то есть 2%. ID выдаются клиентом и передаются в `X-Lab-Request-ID`, поэтому конкурентный порядок прихода запросов не меняет выбранные запросы.

TLS fixture использует локальный тестовый сертификат. Клиент доверяет именно этому сертификату через `RootCAs`; проверка сертификата не отключается. Задержка находится в серверном `GetConfigForClient`, поэтому она действительно входит в наблюдаемый TLS handshake. Она моделирует ожидание на этом этапе, а не вычислительную стоимость криптографии.

DNS fixture — небольшой локальный UDP-сервер, который отвечает A=127.0.0.1 и пустым AAAA для `fixture.test`. Клиент использует `net.Resolver{PreferGo:true}` с этим сервером. Сон не вставляется в `DialContext` вместо DNS. Fixture не предназначен для использования как полноценный DNS-сервис.

## Файлы результатов

```text
results/
  metadata.json
  summary.json
  summary.csv
  baseline.jsonl
  rare_headers.jsonl
  rare_body.jsonl
  pool_1.jsonl
  pool_8.jsonl
  tls_reuse.jsonl
  tls_no_reuse.jsonl
  dns_delay.jsonl
  header_timeout.jsonl
  body_timeout.jsonl
```

Каждая строка JSONL — один клиентский вызов. Строки записываются по ID после завершения серии, поэтому запись JSON на диск не входит в измеренную задержку отдельного запроса. Сортировка по ID не означает хронологический порядок завершения; для него есть `started_at` и события.

Основные поля записи:

| Поле | Значение |
|---|---|
| `duration_ms` | Вся операция до чтения тела и `Close`, либо до ошибки `Do`; включает небольшой накладной расход инструментирования |
| `headers_ms` | От начала операции до успешного возврата `Client.Do`; `null`, если заголовки не были успешно получены |
| `body_ms` | От возврата `Do` до завершения чтения и `Close`; `null`, если тело не читалось |
| `do_error` | Ошибка `Do`: сюда могут попасть DNS, dial, TLS, ожидание заголовков и отмена контекста |
| `body_error` | Ошибка `io.Copy(io.Discard, resp.Body)`, включая deadline после заголовков и усечённое тело |
| `close_error` | Ошибка `resp.Body.Close()` |
| `timed_out` | Широкий признак timeout: `errors.Is(context.DeadlineExceeded)` или `net.Error.Timeout()` |
| `status`, `protocol`, `body_bytes` | HTTP-статус, протокол ответа и число фактически прочитанных байтов тела |
| `fixture_slow` | Сервер вернул `X-Lab-Slow: true`; при ошибке до заголовков этот признак недоступен |
| `events` | Массив исходных callbacks и локальных маркеров чтения/закрытия тела |
| `intervals` | Диагностические интервалы, построенные из событий |
| `trace_snapshot_ms` | Момент снимка событий относительно начала операции |

`do_error`, `body_error` и `close_error` отсутствуют в JSON, если соответствующей ошибки нет. HTTP 200 сам по себе не означает успешного чтения ответа: `body_timeout` специально проверяет этот случай.

`timed_out` не определяет источник дедлайна. Например, таймаут ожидания заголовков также может совпадать с `context.DeadlineExceeded`. Сопоставляйте поле ошибки, последний callback и конфигурацию бюджета.

## Как читать httptrace

Записываются `GetConn`, `GotConn`, `DNSStart`, `DNSDone`, `ConnectStart`, `ConnectDone`, `TLSHandshakeStart`, `TLSHandshakeDone`, `WroteRequest`, `GotFirstResponseByte` и `PutIdleConn`. К ним добавлены `DoReturned`, `BodyEOF` или `BodyReadError`, `BodyClosed` и `RequestDone`.

У каждого события есть абсолютное время `at` с часовым поясом и `at_ms` относительно начала операции. Относительное время вычисляется через монотонную составляющую `time.Time`. Recorder защищён mutex: callbacks могут выполняться одновременно. События хранятся массивом; повторный dial или автоматическая повторная попытка `Transport` не перезаписывает предыдущую попытку.

Для `ConnectStart`/`ConnectDone` сохраняются сеть и адрес. Для `GotConn` — `reused`, `was_idle`, `idle_ms`, локальный и удалённый адреса. Для DNS — адреса, признак coalescing и ошибка. Для TLS — версия, ALPN и ошибка. Ошибка записи запроса сохраняется в `WroteRequest`.

| `intervals[].phase` | Границы | Ограничение интерпретации |
|---|---|---|
| `acquire` | `GetConn → GotConn` | Включает ожидание выдачи соединения **и** его установление, если оно понадобилось |
| `dns` | `DNSStart → DNSDone` | DNS callback может отражать совместный lookup; hostname и coalescing остаются в исходных событиях |
| `connect` | `ConnectStart → ConnectDone` для TCP | Отдельный интервал для каждой пары network/address, включая неудачные попытки |
| `resolver_socket` | Не-TCP `ConnectStart → ConnectDone` | Отдельные UDP-сокеты custom DNS resolver; не смешиваются с TCP до HTTP-сервера |
| `tls` | `TLSHandshakeStart → TLSHandshakeDone` | Отсутствует при использовании уже установленного соединения |
| `request_to_first_byte` | Успешный `WroteRequest → GotFirstResponseByte` | Диагностическое время до первого байта; не равно исключительно времени работы приложения на сервере |

**Интервалы пересекаются.** Нельзя складывать `acquire + dns + connect + tls`, а также складывать p95 разных фаз. Для полной операции используйте непосредственно `duration_ms`.

При reused connection отсутствующие DNS/TCP/TLS — это отсутствие операции в данном запросе. Поэтому для фазы без наблюдений в summary записаны `n: 0` и `null` вместо фиктивного нуля миллисекунд.

HTTP/1.1 выбран намеренно: `ForceAttemptHTTP2=false`, пустой `TLSNextProto`, ALPN `http/1.1`. Вывод о лимите соединений и очереди в `pool_1` относится к этому контролируемому режиму. При анализе HTTP/2 отдельно учитывайте multiplexing и лимиты streams.

`httptrace` не выдаёт универсального идентификатора попытки для всех callbacks. Для DNS/TLS используется FIFO-сопоставление начала и конца; для TCP дополнительно учитываются network/address. Если трасса содержит сложные повторы или параллельные dials, сначала смотрите исходные события. Незавершённые интервалы не превращаются в нулевые длительности. При новой `GetConn` старая незавершённая пара `WroteRequest → first byte` сбрасывается. Если первый байт пришёл раньше `WroteRequest` (например, ранний ответ), отрицательный интервал не создаётся и не заменяется нулём.

Есть явная граница снимка: callbacks, пришедшие **после** `trace_snapshot_ms`, в JSON не попадут. Это возможно для фонового dial после отмены запроса. Recorder при этом остаётся безопасным для конкурентных callbacks; он не обещает ждать их неопределённо долго. Завершение запроса и завершение всех фоновых действий `Transport` — разные события.

## Процентили, ошибки и нагрузка

Используется **nearest rank** без интерполяции: для отсортированных значений `x` процентиль равен `x[ceil(p*n)-1]`, где p=0.50, 0.95 или 0.99. В серии из 500 запросов p99 — 495-е значение. При 10 медленных запросах p50 и p95 могут остаться около baseline, а p99 попадёт в медленный хвост.

В summary есть три раздельные выборки:

- `latency_all`: все запросы, включая ошибки и timeout;
- `latency_completed`: тело успешно прочитано и закрыто; HTTP 4xx/5xx учитываются здесь, если не было I/O ошибки;
- `latency_errors`: запросы с ошибкой `Do`, чтения тела или `Close`.

`requests = completed_responses + io_errors`. Дополнительно указаны `do_errors`, `body_errors`, `close_errors`, `timeouts`, `http_error_responses` для статусов ≥400 и распределение `status_codes`. Timeout остаётся в знаменателе. Сокращение измеренной задержки из-за более раннего отказа не является улучшением успешного обслуживания.

`phases` содержит распределение **наблюдённых интервалов**. Его `n` может отличаться от числа запросов: DNS мог не выполняться, а TCP dial мог иметь несколько попыток. `got_conn_new_events` и `got_conn_reused_events` — число событий выдачи соединения, а не глобальный счётчик всех сокетов процесса.

Нагрузка замкнутая: каждый из `c` работников начинает следующий запрос только после завершения предыдущего. Такой режим удобен для диагностики конкретного ожидания. Он не задаёт независимый поток arrivals и не устраняет coordinated omission; этот инструмент не заменяет испытание на пропускную способность или production-метрики.

Сравнивайте числа только внутри согласованных условий. Сохраняйте версию Go, систему и параметры опыта вместе с результатами; не ожидайте совпадения длительностей до миллисекунды при повторе.

## Отдельные server и probe

В первом терминале:

```sh
./timeoutlab serve -listen 127.0.0.1:18080 -header-delay 25ms
```

Во втором:

```sh
./timeoutlab probe \
  -url http://127.0.0.1:18080/ \
  -n 100 -c 8 -max-conns 1 \
  -timeout 2s -dial-timeout 1s -header-timeout 1s \
  -out results-probe/pool-1.jsonl

./timeoutlab probe \
  -url http://127.0.0.1:18080/ \
  -n 100 -c 8 -max-conns 8 \
  -out results-probe/pool-8.jsonl
```

`probe` сохраняет `pool-1.jsonl` и `pool-1.jsonl.summary.json`, затем печатает summary в stdout. При `-out -` JSONL идёт в stdout, а summary — в stderr. Измеренные сетевые ошибки не останавливают серию и не делают exit status ненулевым: смотрите счётчики в summary. Ненулевой код выхода означает ошибку запуска, параметров или сохранения результата.

Полезные параметры:

| Флаг | Значение по умолчанию | Смысл |
|---|---|---|
| `-n`, `-c` | 200, 8 | Число запросов и работников |
| `-max-conns` | 0 | Лимит активных/устанавливаемых/idle соединений на host; 0 снимает этот лимит |
| `-timeout` | 2s | `http.Client.Timeout`, включая чтение тела; 0 отключает |
| `-request-timeout` | 0 | Отдельный deadline контекста каждого запроса; 0 отключает |
| `-dial-timeout` | 1s | Бюджет `net.Dialer`, включая DNS; 0 отключает |
| `-tls-timeout` | 1s | `TLSHandshakeTimeout`; 0 отключает |
| `-header-timeout` | 1s | `ResponseHeaderTimeout`; чтение тела не покрывает; 0 отключает |
| `-no-reuse` | false | Отключить HTTP connection reuse, а не настроить TCP keepalive |
| `-dns-server` | пусто | Явный DNS-сервер `host:port` для Go resolver |
| `-proxy-env` | false | Применять `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`; исходный режим — прямое соединение |
| `-ca-file` | пусто | Добавить доверенные PEM-сертификаты при проверке HTTPS |
| `-name` | probe | Название сценария в JSON |

Редиректы не выполняются: 3xx остаётся одним измеренным HTTP-ответом. Автоматические повторы, которые сам `Transport` допускает в отдельных обстоятельствах, не запрещены; для них и нужны массивы trace-событий.

Параметры fixture-сервера: `-header-delay`, `-body-delay`, `-slow-every`, `-slow-stage headers|body`, `-slow-delay`. `serve` запускает HTTP/1.1 без TLS. Полный HTTPS-эксперимент с доверенным тестовым сертификатом находится в `suite`.

Дополнительные Linux-сценарии с Docker, `tc netem`, `ss` и `tcpdump` описаны отдельно в `network/README.md`. Сетевые impairment-сценарии требуют отдельного запуска и не являются измерениями из локального `suite`.

## Исходники и проверки

| Файл | Ответственность |
|---|---|
| `trace.go` | Конкурентный recorder и диагностические интервалы |
| `client.go` | Общий transport/client, чтение и закрытие тела, fixed-worker workload |
| `stats.go`, `types.go` | Схема JSON, nearest-rank процентили, раздельные счётчики ошибок |
| `fixtures.go` | Локальные HTTP/TLS/DNS fixtures |
| `suite.go` | Десять экспериментов, CSV/JSON summary, metadata |
| `main.go` | Команды `suite`, `probe`, `serve` |
| `*_test.go` | Реальные локальные сокеты, усечённое тело, body/header timeout, reuse, redirect, DNS/TLS, trace concurrency, знаменатели и хвостовые процентили |

Тесты проверяют наблюдаемое поведение, а не совпадение задержек с точным числом миллисекунд. Искомые свойства: ошибка тела не теряется после успешного `Do`, timeout остаётся в выборке, общее соединение действительно переиспользуется, DNS создаёт реальные resolver callbacks, параллельные callbacks не теряются и JSON сохраняет все измеренные запросы.

Справочники стандартной библиотеки: [`net/http`](https://pkg.go.dev/net/http), [`net/http/httptrace`](https://pkg.go.dev/net/http/httptrace), [`net.Dialer`](https://pkg.go.dev/net#Dialer), [`net.Resolver`](https://pkg.go.dev/net#Resolver). Поведение конкретной версии сверяйте с установленным toolchain; локальный результат не является обещанием идентичных таймингов в другой версии Go или операционной системе.
