# Дополнительная лаборатория: задержка и потери пакетов

Сценарии создают изолированный стенд и сохраняют результаты локально. В репозитории опубликован [проверенный прогон от 12 ноября 2026 года](../../runs/20261112T123100Z/README.md), включая шесть исходных PCAP и измерения всех трёх сетевых сценариев. Новые запуски сохраняйте отдельно.

Это диагностическое внесение сетевых помех. Оно помогает сопоставить HTTP-трассу, TCP-счётчики и захват пакетов. Это не реалистичный тест пропускной способности или ёмкости сервиса: генератор работает по закрытой модели с фиксированными `c` конкурентными работниками, а `netem` установлен на **egress сервера**. Руководство `tc-netem` отдельно предупреждает о TSQ и рекомендует ingress принимающей стороны для реалистичных TCP performance-тестов.

## Что запускается

Два контейнера находятся в отдельной внутренней bridge-сети Compose. Порты на хост не публикуются, host network не используется. Сервер отвечает HTTP/1.1 и задерживает заголовки на 5 мс. Клиент во всех трёх случаях выполняет 1000 запросов, до 8 одновременно, с общим таймаутом запроса 5 с и повторным использованием соединений внутри каждого запуска.

| Случай | Правило на `eth0` сервера |
|---|---|
| `baseline` | Исходный qdisc нового контейнера, без добавленного `netem` |
| `delay20ms` | `netem delay 20ms` |
| `delay20ms-loss1pct` | `netem delay 20ms loss random 1%` |

**20 мс здесь — добавленная задержка исходящего пакета сервера, а не настройка двустороннего RTT в 20 мс.** Правило затрагивает также SYN-ACK, ACK и другие исходящие TCP-пакеты сервера. Потеря 1% задаётся для пакетов, проходящих через этот qdisc; она не означает 1% ошибочных HTTP-запросов. Случайная последовательность потерь не закреплена seed, поэтому разные запуски различаются.

Каждый случай запускает новый процесс клиента, следовательно, начинает с нового пула соединений. Установка `-max-conns 8` фиксирует предел соединений. `-header-timeout 0` убирает отдельный более короткий предел ожидания заголовков: остаются общий лимит 5 с и явно заданный dial timeout 5 с. В этом HTTP-стенде TLS не используется.

## Требования и запуск

Нужны Linux Docker Engine с обычной поддержкой сетевых capabilities, современный Docker Compose v2 с `up --wait`, Bash и GNU coreutils (`timeout`). Rootless Docker и нестандартные сетевые backend могут не поддерживать нужные операции `tc`/захвата. Для сборки нужен доступ к реестру образов и Debian-репозиториям; во время эксперимента сеть контейнеров внутренняя.

Каталог `network/` должен лежать внутри Go-модуля `http-timeout-lab`, рядом с `go.mod` уровнем выше. Dockerfile собирает CLI командой `go build .` из контекста `..`; внешних Go-зависимостей нет. По умолчанию выбран образ компилятора `golang:1.27.4-bookworm`, в соответствии с версией компилятора основного примера. Образ linux/arm64 и пакеты собраны и проверены запуском; фактические digest и версии сохранены в новом каталоге runs/20261112T123100Z. Для строгого повторения эксперимента закрепите также digest образов и версии пакетов.

Из каталога Go-модуля `http-timeout-lab` (на Mac используйте Homebrew Bash 5 и GNU timeout):

```bash
bash network/run.sh ./artifacts/network
```

Параметры при необходимости задаются явно:

```bash
LAB_N=1000 LAB_C=8 LAB_CASE_TIMEOUT_SECONDS=900 \
  bash network/run.sh ./artifacts/network
```

Появится новый каталог `run-<UTC>-<случайный-суффикс>`. Предыдущие данные не перезаписываются. Запускайте сценарий от пользователя, которому доступны команды Docker: pcaps записывает хостовый shell, а процесс `probe` внутри контейнера запускается с UID:GID этого пользователя. Это сохраняет владение JSONL и pcap у вызывающего пользователя; каталог создаётся с закрытыми правами `mktemp`.

Серверу дополнительно назначены `NET_ADMIN` и `NET_RAW`, клиенту — только `NET_RAW`. Стандартный набор Docker capabilities сохранён, в том числе для смены пользователя, выполняемой Debian tcpdump. `tcpdump -p` не включает promiscuous mode. Операции `tc` выполняются исключительно внутри нового контейнера сервера. Сценарий проверяет готовность сервера; после первого успешного TCP healthcheck ставится маркер, чтобы последующие healthcheck не добавляли TCP-трафик в счётчики эксперимента.

## Какие файлы получатся после запуска

Для каждого имени случая:

| Файл | Содержание |
|---|---|
| `<case>.jsonl` | Измерение каждого запроса, включая ошибки и таймауты |
| `<case>.jsonl.summary.json` | Сводка, которую пишет CLI |
| `<case>.client.pcap`, `<case>.server.pcap` | Реальные захваты обеих сторон, фильтр `tcp port 8080` |
| `<case>.<side>.capture.stderr` | Сообщения tcpdump, число захваченных пакетов и dropped by kernel |
| `<case>.<side>.nstat.before.txt`, `.after.txt` | Абсолютные TCP/IP-счётчики namespace, снятые `nstat -asz` |
| `<case>.<side>.nstat.delta.csv` | Разности счётчиков после и до случая |
| `<case>.<side>.tc.before.txt`, `.after.txt` | Действующий qdisc, очереди и счётчики `tc -s -d` |
| `<case>.<side>.retransmissions.csv` | Пакеты, отмеченные tshark как retransmission, fast retransmission или spurious retransmission |
| `<case>.<side>.tshark.stderr` | Диагностика чтения pcap |
| `<case>.probe.stdout`, `.probe.stderr` | Вывод генератора |

Также сохраняются параметры, версии инструментов, развёрнутая Compose-конфигурация, логи сборки/запуска/остановки и `status.txt`. **Проверяйте `measurements_complete=true` и `exit_status=0`.** При ошибке или прерывании сохранённый каталог может содержать частичные JSONL и pcap; это не завершённый результат.

Сначала прочитайте `*.capture.stderr`: потери в механизме захвата отличаются от потерь исследуемой сети. Затем сопоставляйте исходные pcap, `TcpRetransSegs` и другие счётчики с хвостом времени запросов. `nstat` относится ко всему network namespace и не является счётчиком отдельных HTTP-запросов; остаточный трафик завершённых соединений тоже возможен. Метки tshark — результат анализа наблюдаемых sequence/ACK, а не доказательство конкретного места потери. Захват исходящего пакета на сервере также не доказывает, что пакет прошёл последующую обработку qdisc и достиг клиента. `tcp.stream` локален для файла: между двумя pcap сопоставляйте адреса, порты и raw sequence/ACK. Учитывайте offload и полноту обоих захватов.

1000 наблюдений и один случайный прогон не дают устойчивой оценки промышленного p99. Сохраняйте число наблюдений, частоту ошибок и модель нагрузки. Закрытая модель уменьшает создаваемую нагрузку во время задержек; это ограничивает переносимость percentiles на поток независимых поступающих запросов. Не подменяйте длительность до таймаута неизвестной длительностью успешного завершения.

## Завершение и очистка

`EXIT`, `INT` и `TERM` запускают очистку. Сначала tcpdump в обоих контейнерах получает SIGINT для записи финальной статистики, затем выполняется `docker compose down` **только для уникального проекта этого запуска**. Есть отдельные watchdog-лимиты у генератора, tcpdump и операций остановки. Лимит случая по умолчанию — 900 с; при его превышении весь запуск помечается незавершённым. Файлы на хосте сохраняются.

Если хост был выключен, процесс получил SIGKILL или Docker daemon перестал отвечать, shell trap не гарантирует очистку. Имя своего проекта и выходной каталог найдите в `metadata.txt`; после восстановления Docker можно завершить именно его:

```bash
# Подставьте ровно значения compose_project и output_dir из своего metadata.txt.
LAB_PROJECT='timeoutlab-...' LAB_OUTPUT_DIR='/absolute/path/to/run-...' \
  docker compose -p 'timeoutlab-...' -f network/compose.yaml down --timeout 5
```

Не применяйте приведённые правила `tc` к рабочему интерфейсу хоста.

## Проверка результатов

Успешный запуск должен содержать `measurements_complete=true`, `exit_status=0` и `cleanup_exit_status=0`. Дополнительно проверьте все шесть PCAP, число JSONL-записей, HTTP-пары, TCP-счётчики и статистику захвата. Команды полного анализа находятся в [корневом README](../../README.md).

Пять файлов probe (CPU и сеть) используют общее поле `scenario: probe`. Разделяйте сценарии по каталогу и имени файла; не объединяйте их по полю scenario. Не перезаписывайте предыдущие результаты.
